# ADR-002: База данных — PostgreSQL 17 + TimescaleDB + PostGIS

**Status:** Accepted (16.10.2026) · **Date:** 2026-10-16

## Context
Временные ряды измерений (до 100 станций × 6+ веществ, часовые/минутные и разовые пробы, хранение без ограничения), агрегации час/день/месяц, геоданные (станции, границы областей/районов, полигоны CAP), транзакционные данные админки и CMS.

## Decision
Один PostgreSQL 17 с расширениями TimescaleDB (гипертаблица `measurements`, continuous aggregates, сжатие) и PostGIS (геометрии). Образ `timescale/timescaledb-ha:pg17`.

## Options Considered
| Вариант | Complexity | Cost | Scalability | Familiarity | Итог |
|---|---|---|---|---|---|
| A. PostgreSQL + Timescale + PostGIS (выбрано) | Low | Один инстанс | Сотни млн строк на одном хосте | Высокая | Всё в одной БД, один бэкап |
| B. Чистый PostgreSQL с партиционированием | Low | Один инстанс | Хорошая, но агрегаты руками | Высокая | Теряем continuous aggregates и сжатие |
| C. ClickHouse/InfluxDB для рядов + Postgres для остального | High | Два хранилища | Избыточная | Средняя | Неоправданно для объёма |

## Trade-off Analysis
Объём данных мал по меркам Timescale; главная выгода — готовые агрегаты и сжатие при нулевой дополнительной инфраструктуре. Риск — расширения усложняют мажорные апгрейды PG; runbook это покрывает.

## Consequences
- Проще: один `pg_dump`, SQL‑аналитика, PostGIS‑запросы «станции в регионе».
- Сложнее: миграции с SQL для гипертаблиц/агрегатов (вне drizzle‑kit diff).
