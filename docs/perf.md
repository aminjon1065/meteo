# Производительность API и страниц

Неделя 8 (hardening), 17.10.2026. Сценарий и скрипты — `infra/perf/` (k6 в Docker), Lighthouse —
`apps/web/lighthouserc.cjs` (job `e2e` в CI).

## 1. Нагрузочная проверка публичного API

Стенд: MacBook (Apple Silicon), production‑сборка web (`next start`, один процесс Node 22),
PostgreSQL 17 + TimescaleDB и Redis в Docker Desktop, база E2E (2 станции, 48 ч измерений,
прогноз на 72 ч, 12 слоёв SILAM). k6 1.4 в Docker, `RATE_LIMIT_API_PER_MINUTE=0`
(лимит 120/мин на IP иначе превращает нагрузку в 429 — это проверено отдельно, см. ниже).

Команда: `VUS=20 DURATION=30s sh infra/perf/run.sh` — 5 сценариев параллельно, по 20 виртуальных
пользователей на маршрут (100 одновременных соединений), пауза 50 мс между запросами.

| Маршрут | Кэш (TTL) | p50 | p95 | p99 | max | Ошибки |
|---|---|---|---|---|---|---|
| `GET /api/v1/stations` | Redis 60 с | 6 мс | 14 мс | 21 мс | 146 мс | 0 % |
| `GET /api/v1/index/current` | Redis 60 с | 6 мс | 14 мс | 20 мс | 169 мс | 0 % |
| `GET /api/v1/forecast/dushanbe` | Redis 300 с | 6 мс | 15 мс | 21 мс | 177 мс | 0 % |
| `GET /api/v1/silam/layers` | Redis 600 с | 6 мс | 14 мс | 21 мс | 165 мс | 0 % |
| `GET /api/v1/stations/{slug}/measurements?range=24h` (без кэша, continuous aggregate) | — | 10 мс | 31 мс | 52 мс | 166 мс | 0 % |

Суммарно **≈ 1 690 запросов/с** при 100 соединениях, 0 ошибок, пороги k6 (`p(95) < 300 мс`,
ошибок < 1 %) выполнены с большим запасом. Первое (некэшированное) обращение к маршрутам
занимает 3–18 мс (`index/current` — самый тяжёлый: 3 запроса к БД + расчёт по шкалам), далее
ответы отдаются из Redis (`X-Cache: HIT`).

Что сделано для производительности на этой неделе:

- `apps/web/src/lib/cache.ts` — кэш JSON‑ответов четырёх маршрутов в Redis с TTL, равным
  `s-maxage` ответа (60/60/300/600 с); без Redis — ограниченный кэш в памяти процесса; заголовок
  `X-Cache`. Данные меняются раз в 10–60 минут, поэтому минутная задержка публикации допустима.
- Индексы БД не добавлялись: планы запросов используют существующие (`station_index_station_time_idx`,
  `forecast_points_uq`, `silam_fields_time_idx`, гипертаблица `measurements` по времени); при
  нагрузке 100 соединений БД не была узким местом (p99 < 60 мс на самом тяжёлом маршруте).

Повторить на сервере Заказчика после деплоя (ожидаемо медленнее: 4 vCPU, общий хост с БД):
`BASE_URL=https://<домен> VUS=20 DURATION=60s sh infra/perf/run.sh` с временно выставленным
`RATE_LIMIT_API_PER_MINUTE=0` (или с IP‑исключением) — результаты занести в эту таблицу.

## 2. Ограничение частоты запросов

`RATE_LIMIT_API_PER_MINUTE=120` (по умолчанию): 121‑й запрос с одного IP за минуту получает
`429 Too Many Requests`, `Retry-After` и `X-RateLimit-Remaining: 0`; счётчик в Redis, общий для
всех процессов web. Unit‑тесты — `apps/web/src/__tests__/rate-limit.test.ts`; на dev‑сервере
проверено последовательными запросами (`X-RateLimit-Remaining` 119 → 118 → 117). Для виджетов
meteo.tj (несколько запросов на просмотр страницы) лимита достаточно; для серверных интеграций
Агентства лимит поднимается переменной окружения или выделяется отдельный IP.

## 3. Lighthouse

Конфигурация: `apps/web/lighthouserc.cjs` — мобильная эмуляция Lighthouse (медленный 4G, как у
большинства пользователей в Таджикистане), 3 прогона, страницы `/` (tg), `/ru/air/stations/<slug>`,
`/ru/weather`; пороги: performance ≥ 0.80, accessibility ≥ 0.95, SEO ≥ 0.90 (ошибка),
best‑practices ≥ 0.90 (предупреждение). Отчёты — `apps/web/.lighthouseci/`; в CI job `e2e`
падает при нарушении порогов. Локально: `LHCI_REUSE_SERVER=1 pnpm lhci` при запущенном E2E‑сервере.

Результаты 17.10.2026 (production‑сборка, 3 прогона — значения стабильны):

| Страница | Performance | Accessibility | Best practices | SEO | FCP | LCP | TBT | Вес |
|---|---|---|---|---|---|---|---|---|
| `/` (главная, tg) | 86 | 100 | 100 | 100 | 1,1 с | 4,1 с | 120 мс | 2,2 МБ (карта в зоне видимости) |
| `/ru/air/stations/<slug>` | 86 | 100 | 100 | 100 | 1,1 с | 4,1 с | 100 мс | 1,5 МБ |
| `/ru/weather` | 87 | 100 | 100 | 100 | 1,1 с | 4,1 с | 10 мс | 0,5 МБ |

Что исправлено по итогам первого прогона:

- **Падение страницы без WebGL2.** В Chrome Lighthouse (и на старых телефонах) MapLibre бросал
  исключение при создании карты, React поднимал его до error boundary, и Next отдавал пустую
  страницу ошибки (`<html id="__next_error__">` без `lang`, viewport и заголовка — accessibility 0,73).
  Теперь `StationMap`/`LocationPicker` перехватывают ошибку и показывают текст `map.webglUnsupported`.
- **Ленивая загрузка тяжёлых блоков.** `DeferUntilVisible` (`apps/web/src/components/defer-until-visible.tsx`)
  монтирует MapLibre (чанк ≈300 КБ + глифы подложки ≈1 МБ + тайлы) и ECharts (≈180 КБ) только когда
  их контейнер приближается к области просмотра (`IntersectionObserver`, запас 320 px): на странице
  станции performance 64–79 → 86, «неиспользуемый JS» −256 КБ; на главной карта остаётся в первом
  экране на мобильном и грузится сразу.
- **Доступность:** кнопка языка — доступное имя содержит видимый код локали
  (`label-content-name-mismatch`); неактивные вкладки — контраст 4,49 → 5,9 (`text-foreground/70`).

Остаток: LCP ≈ 4,1 с на всех страницах при симуляции медленного 4G — это текст, перерисованный
после загрузки веб‑шрифта Inter (два файла ≈135 КБ, `font-display: swap`). Если потребуется
performance > 90, варианты: `display: "optional"` для шрифта (первое посещение на медленной сети —
системный шрифт), отказ от подмножества `cyrillic-ext`/`latin-ext`, предзагрузка только основного файла.
Решение — с дизайн‑системой (docs/03) и Заказчиком. `bf-cache` не проходит из‑за `Cache-Control: no-store`
динамических страниц Next — на метрики не влияет.
